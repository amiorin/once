Green · OpenTofu · Ansible

Green Once

Use an AI-agent skill to create and operate a production, single-server Basecamp ONCE deployment from a small, reviewable desired-state file.

  • Single server
  • Agent guided
  • Dry-run first
  • MIT licensed

#Introduction

Green Once provisions a server, configures DNS and outgoing email, installs Docker and Basecamp ONCE, and reconciles the applications declared in green.edn. It combines a guided agent skill with an executable infrastructure workflow.

You provide a domain, application images, provider choices, non-secret settings, and public SSH keys. Credentials and application secrets stay in your environment. The result is an isolated set of OpenTofu and Ansible files plus a repeatable lifecycle command.

The safe default Start with build and create --dry-run. Neither command contacts a cloud provider or changes infrastructure. Run a real create only after reviewing the desired state and dry-run.

#green-once and once

Agent interface

green-once

An agent skill that gathers non-secret inputs, creates green and green.edn, protects the work directory with .gitignore, and performs safe build and dry-run checks.

Executable workflow

once

The underlying Green DAG that renders and runs OpenTofu and Ansible stages. It owns provider configuration, state, server setup, application reconciliation, description, and teardown.

The skill is the guided setup and safety layer; the generated green launcher is the durable operational interface. After initialization, the project can be operated directly without Node or the skill.

#Quick start

  1. Use the skill

    Load green-once for a one-off agent session without installing it:

    npx skills use bigconfig-ai/once@green-once

    To install it into an agent permanently instead:

    npx skills add bigconfig-ai/once --skill green-once

  2. Describe the deployment

    Tell the agent the profile name, domain, application hostnames and images, provider choices, and public-key file paths. Give it only the names of environment variables that hold application secrets—never secret values.

    Create a Green Once project for example.com.
Deploy ghcr.io/example/site:latest at www.example.com.
Use DigitalOcean, Resend, Cloudflare, and R2.
Map DATABASE_URL to the key :site-database-url.

  3. Review generated project files

    The skill writes an executable green launcher and a flat green.edn desired-state file. It does not put credentials or application secret values in either file.

  4. Run safe checks

    The skill builds generated configuration and prints the execution graph without provisioning anything:

    ./green build -f ./green.edn
./green create -f ./green.edn --dry-run

  5. Provision explicitly

    Set the required environment variables through your private shell or secret manager, review the dry-run, and explicitly approve the real operation:

    ./green create -f ./green.edn
./green describe -f ./green.edn
Approval boundary The skill must not start a real create or delete merely because initialization succeeded. Those operations require explicit user confirmation.

#Workflow architecture

Green executes the lifecycle as a directed acyclic graph. Independent work runs concurrently; downstream steps receive outputs from their upstream branches.

Create and build

                        ┌─ tofu-compute ─┐
start + validation ─────┤                 ├─ tofu-dns ─ tofu-smtp-post ─┬─ ansible-local
                        └─ tofu-smtp ─────┘                              └─ ansible-remote
1 · Compute + SMTPProvisioned concurrently.
2 · DNSJoins the server IP and SMTP records.
3 · SMTP postVerifies the sending domain after DNS.
4 · Local outputWrites an optional SSH config fragment.
5 · Remote setupInstalls ONCE and reconciles applications.

For build, the same graph renders deterministic configuration with safe placeholder outputs but does not invoke OpenTofu or Ansible.

Delete

start + validation
        │
        └─ ansible-cleanup ─ tofu-smtp-post ─ tofu-dns ─┬─ tofu-smtp
                                                        └─ tofu-compute

A real delete first removes generated Ansible files, then destroys SMTP verification and DNS, and finally destroys SMTP and compute concurrently. Existing OpenTofu outputs are loaded before teardown so dependent state can be addressed in reverse order.

#Desired state

green.edn is a single flat EDN map, except for the nested :once application collection. Keep provider selection and non-secret settings in this file; keep all credentials, passwords, private keys, and application secret values out.

{:profile "production"
 :workdir ".green"
 :domain "example.com"
 :package "once-production"

 :compute-pubkey "ssh-ed25519 AAAA... operator"
 :deploy-pubkey  "ssh-ed25519 AAAA... ci-deploy"

 :once {:applications
        [{:host "www.example.com"
          :image "ghcr.io/example/site:latest"
          :env {"DATABASE_URL" :site-database-url}}]}

 :provider-compute "digitalocean"
 :provider-smtp "resend"
 :provider-dns "cloudflare"
 :provider-backend "r2"
 :compute-prevent-destroy true

 :digitalocean-name "once"
 :digitalocean-region "ams3"
 :digitalocean-size "s-1vcpu-1gb-35gb-intel"
 :digitalocean-image "ubuntu-24-04-x64"
 :digitalocean-ssh-keys "fingerprint-or-id-already-in-the-account"

 :resend-server "smtp.resend.com"
 :resend-port 587
 :resend-username "resend"

 :r2-bucket "once-tfstate"
 :r2-endpoint "https://ACCOUNT_ID.r2.cloudflarestorage.com"}

Non-secret overrides

A GREEN_PAR_* environment variable overrides a flat key. The launcher strips the prefix, lowercases the name, and changes underscores to hyphens. Existing boolean and integer values retain their types.

GREEN_PAR_DIGITALOCEAN_REGION=fra1 ./green build
GREEN_PAR_RESEND_PORT=2525 ./green create --dry-run

Use this mechanism for temporary deployment settings and the destruction guard. Provider credentials should use the provider-native environment variables listed under Secrets and environment.

#Generated files

Every tool gets an isolated directory under <workdir>/<profile>/. With the recommended defaults, a build resembles:

.green/
└── production/
    ├── tofu-compute/
    │   ├── backend.tf.json
    │   └── main.tf.json
    ├── tofu-smtp/
    │   ├── backend.tf.json
    │   └── main.tf.json
    ├── tofu-dns/
    │   ├── backend.tf.json
    │   └── main.tf.json
    ├── tofu-smtp-post/
    │   ├── backend.tf.json
    │   └── main.tf.json
    ├── ansible-local/
    │   └── config
    └── ansible-remote/
        ├── ansible.cfg
        ├── inventory.json
        ├── main.json
        ├── once.json
        ├── mailrc.j2
        ├── files/deploy
        └── library/once
  • The work directory is generated output and should be ignored by Git.
  • Local OpenTofu state remains in each tool directory. S3 and R2 use remote keys of the form <profile>/<tool>.tfstate.
  • Generated Ansible templates contain environment lookups, not application or SMTP secret values.
  • The ansible-local/config file is an SSH fragment you may include from ~/.ssh/config; Green does not overwrite your personal SSH configuration.

#Applications

Applications live in :once {:applications [...]}. Every host must equal :domain or be a subdomain of it, and every application requires a container image.

:once
{:applications
 [{:host "www.example.com"
   :image "ghcr.io/example/site:latest"
   :env {"DATABASE_URL" :site-database-url
         "SECRET_KEY_BASE" :site-secret-key-base}
   :auto_update true
   :auto_backup true
   :backup_path "/var/backups/site"
   :cpus 2
   :memory "2g"}]}

Environment indirection

:env maps a container variable name to the flat green.edn key that holds its value. It never maps to a secret value. The value is supplied by the GREEN_PAR_* variable named after that key — :site-database-url comes from GREEN_PAR_SITE_DATABASE_URL — and the launcher verifies every reference resolves before a real create.

Application keyPurpose
:hostRequired FQDN served by the application.
:imageRequired container image reference.
:envMap of container variable names to the green.edn keys holding their values.
:auto_updateEnable ONCE automatic image updates.
:auto_backupEnable ONCE automatic backups.
:backup_pathSet the application backup path.
:disable_tlsDisable ONCE-managed TLS for the application.
:cpusSet the container CPU allocation.
:memorySet the container memory allocation.

#Secrets and environment

Never put secret values in project files or chat Do not place API tokens, passwords, private keys, access keys, or application secrets in green.edn, the green launcher, prompts, generated examples, logs, or shell history. Use a private environment loader or secret manager.
SelectionRequired environment variablesWhen
DigitalOceanGREEN_PAR_DO_TOKENCreate and delete
Hetzner CloudGREEN_PAR_HCLOUD_TOKENCreate and delete
Oracle CloudNone — authenticates through the :oci-config-file-profile entry in ~/.oci/config—
ResendGREEN_PAR_RESEND_API_KEY, GREEN_PAR_RESEND_PASSWORDCreate and delete
Existing SMTPGREEN_PAR_NO_INFRA_SMTP_PASSWORDCreate and delete
Cloudflare DNSGREEN_PAR_CLOUDFLARE_API_TOKENCreate and delete
R2 backendGREEN_PAR_R2_ACCESS_KEY_ID, GREEN_PAR_R2_SECRET_ACCESS_KEYCreate and delete
S3 backendNone — OpenTofu resolves its own AWS credential chainCreate and delete
Application :envOne GREEN_PAR_* per key named by the application mapCreate

Every credential travels the same path: a GREEN_PAR_* variable overlaid onto the matching flat key. There is no TF_VAR_* or provider-native variable, and no Ansible environment lookup. Build and dry-run do not require these variables — unset values render empty, so a build never writes a secret to disk.

Check presence without printing values

for name in GREEN_PAR_DO_TOKEN GREEN_PAR_RESEND_API_KEY \
  GREEN_PAR_RESEND_PASSWORD GREEN_PAR_CLOUDFLARE_API_TOKEN \
  GREEN_PAR_R2_ACCESS_KEY_ID GREEN_PAR_R2_SECRET_ACCESS_KEY; do
  if [ -n "${!name:-}" ]; then
    printf '%s: set\n' "$name"
  else
    printf '%s: missing\n' "$name"
  fi
done

Adjust the list to your selected providers. This check reports only presence and never prints values.

#Compute providers

DigitalOcean

:provider-compute "digitalocean"
:digitalocean-name "once"
:digitalocean-region "ams3"
:digitalocean-size "s-1vcpu-1gb-35gb-intel"
:digitalocean-image "ubuntu-24-04-x64"
:digitalocean-ssh-keys "fingerprint-or-id-already-in-the-account"
;; Optional:
:digitalocean-vpc-uuid "non-secret-vpc-uuid"

The droplet attaches the key named by :digitalocean-ssh-keys, which must already exist in the account — give it a fingerprint or key id. Credential: GREEN_PAR_DO_TOKEN.

Hetzner Cloud

:provider-compute "hcloud"
:hcloud-name "once"
:hcloud-image "ubuntu-24.04"
:hcloud-server-type "cx23"
:hcloud-location "hel1"
:hcloud-ssh-keys "key-name-or-id-already-in-the-project"

Creates an IPv4 server attached to the key named by :hcloud-ssh-keys, which must already exist in the project. Credential: GREEN_PAR_HCLOUD_TOKEN.

Oracle Cloud Infrastructure

:provider-compute "oci"
:oci-config-file-profile "DEFAULT"
:oci-subnet-id "ocid1.subnet..."
:oci-compartment-id "ocid1.compartment..."
:oci-availability-domain "..."
:oci-display-name "once"
:oci-shape "VM.Standard.A1.Flex"
:oci-ocpus 1
:oci-memory-in-gbs 4
:oci-boot-volume-size-in-gbs 50
:oci-boot-volume-vpus-per-gb 30
:oci-ssh-authorized-keys "/home/user/.ssh/once.pub"

The current default shape is ARM-based. :oci-ssh-authorized-keys is a path to a public-key file on the machine running the launcher; its contents are written into instance metadata at plan time. OCI authenticates through the named profile in ~/.oci/config, so no credential variable is required.

Existing server

:provider-compute "no-infra"
:no-infra-compute-ip "203.0.113.10"
:no-infra-compute-user "root"
:no-infra-compute-sudoer "root"
:no-infra-compute-uid 0
:no-infra-compute-name "once"

No compute resource or API credential is required. The server must be reachable using the configured user and an SSH identity already loaded into ssh-agent. :compute-pubkey may be omitted.

#SMTP providers

Resend

:provider-smtp "resend"
:resend-server "smtp.resend.com"
:resend-port 587
:resend-username "resend"

The SMTP stage creates notifications.<domain>, returns its DNS records, and the post stage verifies it after DNS is configured. Use GREEN_PAR_RESEND_API_KEY for the Resend API and GREEN_PAR_RESEND_PASSWORD for server-side SMTP authentication.

Existing SMTP

:provider-smtp "no-infra"
:no-infra-smtp-server "smtp.example.net"
:no-infra-smtp-port 587
:no-infra-smtp-username "smtp-user"

No SMTP infrastructure is created. A real create still requires GREEN_PAR_NO_INFRA_SMTP_PASSWORD so the remote ONCE server can send mail.

#DNS providers

Managed

cloudflare

Finds the configured zone, creates a proxied A record for each application hostname, and adds the unproxied records returned by Resend. Requires GREEN_PAR_CLOUDFLARE_API_TOKEN with zone-read and DNS-edit access.

External

no-infra

Creates no DNS resources and requires no DNS credential. You are responsible for application and SMTP records outside Green Once.

:provider-dns "cloudflare"  ; or "no-infra"

#State backends

Backend advice writes a backend configuration before every OpenTofu stage. State is isolated by both profile and tool.

Local

:provider-backend "local"

Best for experiments. Protect and back up the work directory; losing local state makes safe lifecycle management difficult.

Amazon S3

:provider-backend "s3"
:s3-bucket "once-tfstate"
:s3-region "eu-west-1"

The generated backend names only the bucket, key, and region, so OpenTofu resolves credentials through its own AWS chain — environment variables, a shared profile, or an instance role. State keys are <profile>/<tool>.tfstate.

Cloudflare R2

:provider-backend "r2"
:r2-bucket "once-tfstate"
:r2-endpoint "https://ACCOUNT_ID.r2.cloudflarestorage.com"

Uses the S3-compatible backend with region = "auto", taking the R2 access key from GREEN_PAR_R2_ACCESS_KEY_ID and GREEN_PAR_R2_SECRET_ACCESS_KEY. State keys are <profile>/<tool>.tfstate.

#SSH configuration

Operations

:compute-pubkey

Accepted but currently unused: each compute provider references a key already registered with it (:digitalocean-ssh-keys, :hcloud-ssh-keys) or a local public-key file (:oci-ssh-authorized-keys). The matching private half should be loaded into ssh-agent before create so Ansible can reach the new server.

Deployment

:deploy-pubkey

Authorizes the remote deploy user through a forced command. Interactive sessions are denied; only sudo once update <configured-host> is accepted.

Public keys are not secrets, but private key files are. The skill may read only a public .pub file that you approve; it must never inspect a private SSH key.

ssh-add -l
ssh deploy@203.0.113.10 sudo once update www.example.com

#Build

./green build

Build validates the selected providers and required non-secret values, then renders all OpenTofu and Ansible files. It does not invoke OpenTofu, Ansible, SSH, or provider APIs. Use it to review exactly what Green Once would generate.

#Create and dry-run

./green create --dry-run
./green create

Dry-run validates desired-state structure and prints planned DAG actions without requiring provider credentials. Real create additionally checks provider and application environment variables, applies the four OpenTofu stages, and configures the host with Ansible.

Real infrastructure operation A real create can incur cloud costs, create public DNS records, and deploy internet-facing applications. Review green.edn, build, and dry-run first.

#Describe

./green describe

Describe reads compute and SMTP outputs from their OpenTofu state, reports the selected providers, probes the server over SSH, and runs sudo -n once list when the host is reachable. Connectivity problems are reported without changing infrastructure.

For a remote backend, make sure its credentials are present so OpenTofu outputs can be read. The compute private key must be available to SSH.

#Delete and dry-run

./green delete --dry-run
GREEN_PAR_COMPUTE_PREVENT_DESTROY=false ./green delete

Dry-run prints teardown order and changes nothing. A real delete is refused while :compute-prevent-destroy is true, which is the required default. Deliberately override it only for the exact delete you have approved.

Destructive operation Delete removes managed DNS, SMTP, and compute resources. Verify backups and state access first. The protection override should be temporary rather than committed to green.edn.

#Using another desired-state file

Use -f or --file with every command:

./green build -f ./production.edn
./green create --file ./production.edn --dry-run
./green describe -f ./production.edn

Keep profiles and work directories distinct to prevent state or generated files from overlapping.

#Safe lifecycle

  1. Keep green.edn free of secrets and commit it for review.
  2. Keep <workdir>/ and private environment files ignored by Git.
  3. Load the compute private key into ssh-agent; never copy it into the project.
  4. Load required credentials through a private environment or secret manager.
  5. Run ./green build.
  6. Run ./green create --dry-run.
  7. Explicitly approve and run ./green create.
  8. Run ./green describe after provisioning.
  9. Back up application data and OpenTofu state before teardown.
  10. Dry-run and explicitly approve any real delete.

For production, prefer S3 or R2 state over local state and protect the bucket with appropriate access controls and retention.

#Application updates

The remote server gets a restricted deploy account intended for CI or controlled update jobs. Its forced command rejects interactive sessions, malformed commands, and hosts not already known to ONCE.

ssh deploy@SERVER_IP sudo once update www.example.com

The key supplied as :deploy-pubkey is the only credential authorized for that account. You can also set :auto_update true on an application when ONCE should handle updates automatically.

Running ./green create again is appropriate when infrastructure or declared application membership changes: the remote Ansible module adds missing hosts and removes hosts no longer present in desired state.

#Troubleshooting

npx skills cannot find green-once

Confirm internet access and use the full package and skill name: npx skills use bigconfig-ai/once@green-once.

A desired-state key is required

Add the missing non-secret field for the selected provider. Remove unused providers' fields rather than filling them with credentials or passwords.

A required environment variable is not set

Set the named variable through your private environment loader or secret manager. Check presence only; do not print the value. Application variable names come from each application's :env map.

:env must map container names...

Use a map, not a vector of KEY=value strings:

:env {"DATABASE_URL" :site-database-url}

Compute destruction is protected

This is expected. First run ./green delete --dry-run. After explicit approval, set GREEN_PAR_COMPUTE_PREVENT_DESTROY=false only for the real delete command.

SSH is not reachable

  • Check the address reported by ./green describe.
  • Run ssh-add -l and confirm the compute private key is loaded.
  • Check provider firewalls and the configured existing-server user.
  • For a fresh cloud server, allow startup and SSH initialization to finish.

OpenTofu output or state is missing

Use the same :profile, :workdir, backend selection, and backend credentials used during create. Do not delete the local work directory when using local state.

Resend verification is delayed

Confirm Cloudflare received all unproxied Resend records and allow DNS propagation. Rerun create after the records are visible; OpenTofu will continue from existing state.

Cloudflare cannot find the zone

The configured :domain must already belong to a zone accessible by GREEN_PAR_CLOUDFLARE_API_TOKEN. The token needs permission to read the zone and edit DNS records.

An existing server fails during create

Verify direct SSH access with :no-infra-compute-user, passwordless privilege escalation for :no-infra-compute-sudoer, a supported Linux host, and outbound network access for installers.
